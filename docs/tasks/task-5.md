Beschreibung
Die Basis steht: Library, Demo-Anwendung, erste Erkenntnisse aus dem API-Test in Issue #4. Dieses Issue ist bewusst offen und liegt in der vorlesungsfreien Zeit. Wählen Sie einen von zwei Wegen.

Weg A: Die Vision-Anwendung

Bauen Sie eine Anwendung, die zeigt, was mit Ihrer Library wirklich möglich ist, wenn man richtig Zeit reinsteckt. Thema frei. Anspruch höher als bei Issue #4: durchdachte Interaktion, sauberes UX, ein Ergebnis, das Sie auch außerhalb der Veranstaltung zeigen würden.

Weg B: Die Vertiefung

Nehmen Sie eine Schwachstelle, die Ihnen beim Bauen aufgefallen ist, und lösen Sie sie richtig. Zum Beispiel: Performance unter Last, Robustheit und Fehlertoleranz der Gestenerkennung, Latenz, Genauigkeit bei schlechten Lichtverhältnissen, Barrierefreiheit, oder ein sauber durchdachtes neues Gestenvokabular. Kein neues Projekt, sondern echte Tiefenarbeit an einem bestehenden Problem.

Entscheiden Sie sich für einen Weg. Beide sind gleichwertig, es geht nicht darum welcher Weg mehr zählt, sondern welcher zu Ihrem Interesse passt.

Akzeptanzkriterien
Gemeinsam für beide Wege:

Begründete Entscheidung für Weg A oder B, kurz dokumentiert: warum dieser Weg, was war die Alternative?
Ergebnis lauffähig, lokal startbar, im Repo eingecheckt (main Branch!)
Ergebnis zusätzlich deployt und über eine öffentlich erreichbare URL abrufbar
Vorgehen und Entscheidungen als Decision Records dokumentiert
Repo enthält eine README, die für fremde Dritte verständlich ist: was das Projekt macht, welche Voraussetzungen es braucht (Node-Version, Abhängigkeiten etc.), wie man es lokal installiert und startet, und wie man es selbst deployt. So nachvollziehbar, dass jemand Fremdes es lokal zum Laufen bringen und weiterentwickeln könnte
Kurzes Video, maximal 10 Minuten, in guter Qualität (YouTube-tauglich), das das Projekt vorstellt und eine Live-Demo enthält. Den Upload Link finden Sie auf dem Miro Board.
Weg A, Vision-Anwendung:

Anwendung nutzt die Library ausschließlich über die öffentliche API
Klar erkennbare gestalterische oder konzeptionelle Idee, nicht nur Funktionsdemo
Kurze Reflexion: Was macht diese Anwendung besonders, was war die größte Herausforderung?
Weg B, Vertiefung:

Problem oder Schwachstelle klar benannt und mit Vorher/Nachher-Messung oder -Beobachtung belegt
Lösung nachvollziehbar begründet, Alternativen kurz erwähnt
Auswirkung auf die restliche Library oder Anwendung dokumentiert: Breaking Changes? Trade-offs?
